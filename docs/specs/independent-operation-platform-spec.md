# 无限画布独立运营平台 Spec

> 状态：实施已批准（Implementation Approved）  
> 当前阶段：M1 后端身份流程与前端账户入口已落地，等待 MySQL/Redis/SMTP 联调验收
> 目标：形成一套独立品牌、独立部署、单一账户与计费体系的无限画布商业版

## 1. 文档使用方式

本文档同时承担产品 Spec、技术边界和实施验收基线三种职责。

- 标记为 **已确定** 的内容，后续实现不得自行偏离。
- 标记为 **建议默认** 的内容，进入实现前仍可讨论调整。
- 标记为 **待确认** 的内容，必须由产品决策冻结后才能落地。
- 每次讨论形成结论后，直接更新本文档的状态和决策记录。
- Spec 冻结后，按第 18 节 SOP 分阶段实施；每阶段完成后单独验收，不跨阶段堆叠未验证功能。

## 2. 产品目标

### 2.1 核心定位（已确定）

无限画布商业版面向最终创作用户，而不是 API 开发者。

用户只需要关心：

1. 我是否已经登录。
2. 我还有多少可用额度。
3. 当前操作预计消耗多少额度。
4. 当前余额大约还能完成多少次同类操作。
5. 余额不足时如何充值。
6. 我的生成任务是否成功，结果在哪里。

用户不需要理解或操作：

- API Key、Token、Base URL；
- 上游供应商、渠道、协议和请求脚本；
- 模型倍率、渠道权重、故障切换；
- 上游错误原文和管理员诊断信息；
- 计费表达式及成本核算方式。

管理员统一负责模型、渠道、定价、消费、订单、异常任务和系统运营。

### 2.2 成功标准（已确定）

- 新用户完成注册或登录后，无需任何 AI 配置即可开始创作。
- 每次付费操作在提交前展示预计消费，完成后展示实际消费。
- 余额不足时不创建上游任务，直接引导充值。
- 同一用户、余额、订单、生成任务和消费流水在一个系统内闭环。
- 管理员可替换模型或渠道，普通用户无需重新配置。
- 单次部署只有一个无限画布业务应用，不依赖第二套 New API 服务。
- 画布项目、节点、素材库和生成结果继续保存在浏览器本地，不建设云端项目与素材系统。

## 3. 非目标

第一阶段不建设以下产品形态：

- 面向开发者的 API 分销平台；
- 普通用户 Token 创建与管理；
- 普通用户自定义渠道、API Key 或请求脚本；
- 普通用户直接选择具体供应商；
- 多租户独立管理后台；
- 套餐订阅、邀请返佣、抽奖、签到等运营体系；
- 企业组织、席位和团队账单；
- 同时运行两套账户或余额系统。

上述能力只有在独立立项并更新本文档后才进入范围。

## 4. 角色与权限

### 4.1 游客

- 浏览公开页面；
- 注册、登录、找回密码；
- 查看公开的充值说明和服务协议；
- 不发起付费生成，不访问用户项目和素材。

### 4.2 普通用户

- 使用画布、工作台、电商项目等创作能力；
- 查看余额、预计消费、实际消费和预计剩余次数；
- 充值并查看自己的订单；
- 只读查看自己的消费明细；
- 管理自己的资料和安全设置，并继续使用浏览器本地项目、素材和生成结果；
- 不查看或修改任何渠道、密钥、内部模型、定价规则和成本信息。

### 4.3 管理员

- 管理用户、角色、状态和人工额度调整；
- 管理产品能力、内部模型、渠道、密钥和路由；
- 管理销售价格、成本价格和生效版本；
- 管理充值套餐、支付渠道、订单和退款；
- 查看全站消费、成本、毛利、任务和错误；
- 对异常任务执行退款、补偿或重试；
- 查看管理员操作审计记录。

第一阶段只设置 `user` 和 `admin` 两类角色。细分客服、财务、运营权限列为后续能力。

## 5. 用户体验

### 5.1 登录与注册

用户端至少包含：

- 注册；
- 登录；
- 退出登录；
- 找回密码；
- 重置密码；
- 当前设备会话失效后的重新登录提示。

首期使用邮箱与密码注册登录，邮箱验证和邮件找回密码；第三方登录不进入首期范围。

### 5.2 全局余额入口

登录后，所有主要创作页面顶部统一展示：

```text
可用额度：123.45
```

点击后进入账户中心，展示：

- 当前可用额度；
- 充值按钮；
- 最近充值记录；
- 最近消费记录；
- 额度变动原因；
- 当前选定操作的预计剩余次数。

### 5.3 “可以用多久”的表达

余额模式下不直接承诺“可使用多少天”。不同图片、视频和文本任务成本差异较大，因此按当前操作显示预计次数：

```text
当前余额：36.80
本次预计：0.42
按当前设置约可再生成 87 张
```

视频示例：

```text
当前余额：36.80
本次预计：3.06
按当前设置约可再生成 12 段 6 秒视频
```

估算仅基于当前参数和当前生效价格，界面需要标注“约”。

### 5.4 生成交互

1. 用户选择创作能力和业务参数。
2. 前端请求服务端报价，不在浏览器自行计算最终价格。
3. 界面展示预计消费和预计剩余次数。
4. 用户确认生成。
5. 服务端校验登录状态、能力状态、价格版本和余额。
6. 服务端预占额度并创建生成任务。
7. 服务端选择内部模型和渠道，调用上游服务。
8. 成功后按实际用量结算；失败后按规则释放预占额度。
9. 前端更新节点、任务状态、余额和消费记录。

### 5.5 用户可见错误

普通用户只看到可行动的产品化提示：

- 余额不足，请先充值；
- 当前能力维护中，请稍后再试；
- 生成失败，本次未消费；
- 任务处理时间较长，可在任务中心继续查看；
- 登录状态已失效，请重新登录。

供应商名称、渠道编号、密钥状态、原始响应体和内部堆栈只进入管理员日志。

## 6. 产品能力与内部模型分离

### 6.1 产品能力（已确定）

用户按能力类别使用管理员发布的模型。产品能力保持稳定，模型名称对用户可见，上游供应商和渠道保持隐藏。建议首批能力标识：

| 能力标识 | 用户名称 | 主要参数 |
| --- | --- | --- |
| `image.generate` | 图片生成 | 数量、比例、质量、背景 |
| `image.edit` | 参考图生成 | 参考图、数量、比例、质量 |
| `video.generate` | 视频生成 | 时长、比例、清晰度、声音 |
| `text.generate` | 智能文案 | 输入内容、输出数量 |
| `audio.generate` | 音频生成 | 声音、格式、速度 |
| `image.qa` | 图片检查 | 商品资料、待检查图片 |

管理员可将一个产品能力绑定到一个或多个模型，并配置用户可见模型名称、价格、上下线状态和路由优先级。普通用户可以看到并选择管理员发布的模型名称。

### 6.2 内部模型

模型记录至少包括：

- 内部 ID；
- 用户可见模型名称；
- 上游模型名称；
- 能力类型；
- 支持的参数范围；
- 请求协议或适配器；
- 是否启用；
- 成本规则；
- 销售计价规则；
- 可用渠道集合；
- 默认路由策略。

普通用户接口返回管理员发布的模型 ID、模型名称、能力类型、支持参数和销售价格摘要，不返回上游供应商、渠道密钥、成本价、内部路由和管理员备注。

### 6.3 路由

管理员配置能力到模型、模型到渠道的映射。路由需要支持：

- 启用和停用；
- 优先级与权重；
- 能力参数校验；
- 渠道健康状态；
- 失败切换；
- 同一任务固定路由上下文；
- 异步任务后续查询仍使用原渠道。

首期统一规则：同步图片/文本请求超时 120 秒；只有确认请求尚未被上游接受时才允许最多重试 1 次；获得远端任务 ID 后禁止自动换渠道重复提交；每个用户同时最多运行 3 个生成任务。视频、音频等异步任务后续查询固定使用原渠道。

## 7. 账户与安全

### 7.1 会话

建议默认使用服务端会话和 HttpOnly Cookie：

- 浏览器不持有模型调用 Token；
- 会话支持主动退出和管理员强制失效；
- 用户会话有效期 7 天，有操作时滑动续期，最长连续 30 天；
- 密码重置后撤销该用户全部现有会话；
- 管理员账号支持更高等级的登录保护。

### 7.2 密码与验证

- 密码只保存成熟密码哈希；
- 注册验证、重置凭据和验证码均为一次性用途；
- 找回密码不得泄露账号是否存在；
- 登录、注册、找回密码和支付接口需要限流；
- 邮箱验证链接和密码重置链接有效期均为 30 分钟；
- 同账号或 IP 在 15 分钟内登录失败 5 次后冷却 15 分钟。

### 7.3 管理员审计

以下操作必须记录管理员、对象、变更前后摘要、原因和时间：

- 人工调整额度；
- 退款与补偿；
- 用户封禁和解封；
- 渠道密钥或路由变更；
- 模型定价发布；
- 支付配置变更；
- 系统开关变更。

敏感字段只记录脱敏摘要，不进入审计正文。

## 8. 钱包与账务

### 8.1 基本原则（已确定）

- 所有金额和额度使用整数最小单位存储；
- 余额是聚合结果，账务流水是事实来源；
- 流水追加后保持不可变；
- 人工修正通过新增调整流水完成；
- 每次余额变化都有唯一业务幂等键；
- 余额更新与流水写入在同一数据库事务中完成；
- 用户余额不得由前端提交的新余额值覆盖。

### 8.2 额度来源

建议区分：

- 充值额度：用户实际付款获得；
- 赠送额度：注册、活动或管理员赠送；
- 邀请额度：邀请人和被邀请人按管理员配置获得；
- 补偿额度：异常任务补偿；
- 退款额度：订单退款或生成任务结算返还。

首期采用统一可用额度，不拆分用户可见子账户；流水必须记录充值、赠送、邀请、补偿和退款来源。赠送额度首期不过期，所有来源统一参与消费。

### 8.3 流水类型

- 充值入账；
- 生成预占；
- 生成结算；
- 预占释放；
- 支付退款；
- 管理员增加；
- 管理员扣减；
- 活动赠送；
- 邀请奖励；
- 系统补偿。

每条流水至少关联用户、业务幂等键、业务对象、变动值、变动后余额、额度来源、价格快照和备注。

## 9. 报价、预占与结算

### 9.1 报价

服务端根据以下内容生成报价：

- 产品能力；
- 当前参数；
- 当前有效销售价格版本；
- 输出数量；
- 可预估的文本、图片、音频或视频用量。

报价返回：

- `quoteId`；
- 预计额度；
- 价格版本；
- 有效状态；
- 用户可读的计价摘要。

报价有效期为 5 分钟；过期后重新报价，不创建生成任务。

### 9.2 预占

创建生成任务时必须使用服务端签发的报价，并在同一事务中：

1. 校验报价仍有效；
2. 校验参数没有被篡改；
3. 校验余额；
4. 创建任务；
5. 预占额度；
6. 写入流水和价格快照。

重复提交同一幂等键只返回原任务，不重复预占。

### 9.3 结算

- 固定价格任务按成功数量结算；
- 按 Token、秒数或上游实际用量计费的任务按实际结果结算；
- 实际费用低于预占时释放差额；
- 实际费用高于预占时，用户最多扣除预占额度，差额计入平台异常成本，不产生用户负余额；
- 部分成功的多结果任务按成功结果结算，失败部分释放；
- 结算使用任务创建时冻结的价格快照，不读取后来修改的新价格。

### 9.4 失败处理

| 场景 | 默认结算建议 |
| --- | --- |
| 余额不足 | 不创建上游任务，不扣费 |
| 参数校验失败 | 不创建上游任务，不扣费 |
| 渠道不可用且未发出请求 | 全额释放 |
| 上游明确失败且没有结果 | 全额释放 |
| 多结果部分成功 | 仅结算成功部分 |
| 异步任务超时但上游状态未知 | 保持待核查，不立即重复提交 |
| 结果已生成但客户端下载失败 | 任务保持成功，允许重新下载 |
| 管理员确认异常 | 通过补偿或退款流水处理 |

异步未知状态保留 24 小时，期间只查询原任务、不重复提交；到期后进入管理员人工核查。

## 10. 充值与支付

### 10.1 用户流程

1. 用户选择充值金额或充值套餐。
2. 服务端创建充值订单。
3. 用户完成支付。
4. 支付渠道向服务端发送异步回调。
5. 服务端验签并按支付流水号幂等处理。
6. 订单更新为已支付，钱包入账并写入流水。
7. 前端通过订单查询获得最终状态。

前端跳转成功页不能作为到账依据。

### 10.2 订单状态

建议状态：

```text
pending -> paid
pending -> closed
paid -> refunding -> refunded
paid -> refund_failed
```

支付模块沿用 New API 的配置和订单流程。首期只启用易支付；Stripe、Creem、Waffo 保留后续扩展位。支付订单有效期为 30 分钟，单笔充值最低 1 元、最高 5000 元；到期订单关闭，迟到回调进入人工核查。

### 10.3 支付可靠性

- 回调验签；
- 渠道支付流水号唯一；
- 重复回调只处理一次；
- 入账和订单状态在同一事务中完成；
- 支持主动查询订单状态；
- 支持管理员对账和异常订单处理；
- 所有退款保留原订单和退款流水关联。

### 10.4 邀请奖励

- 每个用户拥有唯一邀请码和邀请链接；
- 注册时可绑定一名直属邀请人，绑定后用户不能自行修改；
- 禁止邀请自己、重复绑定和形成循环邀请关系；
- 管理员可配置邀请功能开关、邀请人奖励额度和被邀请人奖励额度；
- 奖励金额、配置版本、邀请关系和受益人保存快照；
- 同一邀请关系的同一奖励类型只能成功入账一次；
- 奖励进入统一可用额度，同时写入独立邀请奖励记录和不可变额度流水；
- 管理后台可查看邀请关系、奖励状态、风险事件，并执行补发或作废；
- 用户端可查看邀请码、邀请链接、脱敏下级列表和自己的奖励记录。

奖励发放时点、单用户累计上限、单日上限和风险审核阈值仍需确认。

## 11. 生成任务

任务统一承载图片、视频、文本、音频和 QA 调用。

建议状态：

```text
created
reserved
dispatching
processing
succeeded
partially_succeeded
failed
canceled
review_required
```

任务至少保存：

- 用户归属和本地项目关联标识；
- 产品能力与请求参数摘要；
- 输入素材引用；
- 选定模型和渠道快照；
- 上游任务 ID；
- 报价和价格快照；
- 预占、结算和退款状态；
- 输出结果引用或必要的临时地址；
- 用户错误信息和管理员诊断信息；
- 幂等键和创建来源。

服务端任务只保存计费、异步查询和审计所需的元数据。任务成功后，浏览器按现有流程把结果写入本地画布节点和本地素材库。

## 12. 管理后台

### 12.1 仪表盘

- 注册用户与活跃用户；
- 充值金额；
- 用户消费；
- 上游成本；
- 毛利估算；
- 成功率与平均处理时间；
- 待核查任务；
- 渠道健康状态。

### 12.2 用户管理

- 搜索和筛选；
- 查看余额与流水；
- 封禁、解封；
- 人工增加或扣减额度；
- 查看订单和生成任务；
- 强制会话失效；
- 操作必须填写原因。

### 12.3 产品能力与模型

- 产品能力上下线；
- 用户显示名称和说明；
- 参数约束；
- 默认内部模型；
- 备用模型；
- 销售价格版本；
- 成本与毛利预览。

### 12.4 渠道

- 渠道类型、地址和密钥；
- 模型映射；
- 优先级、权重和状态；
- 健康检查；
- 使用量、错误率和成本；
- 密钥脱敏展示；
- 渠道测试由管理员主动执行。

### 12.5 财务与消费

## 15. 技术架构

### 15.1 模块化单体（已确定）

```text
web/          React + Vite 用户端和 Ant Design 管理后台
controller/   HTTP 接口
service/      业务、计费与结算
model/        GORM 模型
middleware/   身份、权限和限流
relay/        模型请求与渠道适配
setting/      系统、支付、模型与渠道配置
migrations/   MySQL 数据迁移
deploy/       单体部署配置
```

一个 Go 进程提供业务 API，并托管 `web/dist` 静态资源。生产环境使用一套业务应用、一个 MySQL 和一个 Redis；画布项目与素材不上传对象存储。

这是一套独立产品，不运行第二个 New API 进程。

### 15.2 服务端模块

```text
controller / service / model：账号、用户、钱包、支付、生成任务、管理后台
middleware：身份、权限、限流和分发
relay：图片、视频、文本和音频请求适配
setting：支付、模型、渠道、倍率和系统配置
common：JSON、缓存、加密和额度工具
```

保持 Router -> Controller -> Service -> Model 分层，账务、支付回调和任务结算不得直接在 Controller 中拼装。

### 15.3 基础设施

- 数据库：生产固定使用 MySQL；
- Redis：会话、限流、分布式锁、队列或任务状态；
- 邮件或短信服务：注册验证与找回密码；
- 支付服务：沿用 New API 的支付配置结构和已支持渠道，由管理员选择启用项。

### 15.4 本地模式与运营模式

当前项目是浏览器本地数据和用户自备密钥模式。商业版需要明确：

- **运营模式**：必须登录，AI 请求只走服务端，普通用户不显示密钥配置；项目、节点、素材和结果仍保存在浏览器本地；
- **本地模式**：继续保留用户自备 Key 的独立入口或独立部署模式；
- 两种模式不得共享同一个含义不清的配置状态；
- 运营模式的账户、额度、订单、消费和生成任务归属以服务端用户 ID 为准；画布与素材归属仍以当前浏览器本地数据为准。

## 17. 验收基线

### 17.1 用户端

- 新用户从注册到首次生成不接触任何密钥或渠道配置；
- 未登录访问受保护页面时进入登录流程，并能返回原页面；
- 生成前显示服务端报价；
- 余额不足时不产生上游请求；
- 成功、失败、部分成功都产生一致的余额和流水结果；
- 刷新页面后异步任务和余额状态一致；
- 用户只能看到自己的在线账户、订单、流水和任务；画布项目与素材继续由当前浏览器本地隔离。

### 17.2 管理端

- 管理员能完整配置一个产品能力、模型、渠道和价格并发布；
- 切换渠道后用户界面和项目配置无需变化；
- 密钥在列表、日志和审计中保持脱敏；
- 人工调账、退款和补偿都有原因与审计记录；
- 能定位任一用户生成任务对应的报价、预占、结算、渠道和结果。

### 17.3 账务与支付

- 重复生成提交不会重复预占；
- 重复支付回调不会重复入账；
- 并发消费不会产生负余额；
- 失败和部分成功按冻结价格结算；
- 退款、补偿和管理员调整不改写历史流水；
- 聚合余额与流水汇总可核对。

### 17.4 发布

- 发布前项目自有 GitHub 与 Gitee 分支指向同一提交；
- 数据库迁移前有可恢复备份；
- 应用、登录、支付回调、生成任务和管理后台均有健康检查；
- 发布失败可回滚应用和数据库迁移；
- 发布完成后清理本地制品、缓存和远端 staging，保留回滚备份与业务数据。

## 19. 冻结决策

### 已确认架构决策

1. 基于 New API 相关组件实施，保留许可证、来源与归属要求。
2. 登录采用邮箱与密码，使用邮件验证和邮件找回密码。
3. 用户余额显示“额度”，充值页面显示人民币金额和到账额度。
4. 支付沿用 New API 的配置方式，由管理员启用具体渠道。
5. 所有运营模式 AI 生成功能要求登录。
6. 本地自备 Key 模式继续保留，但与运营模式使用独立入口或部署配置。
7. 生产数据库固定使用 MySQL。
8. 项目、画布节点、素材和生成结果继续保存在浏览器本地。
9. 管理后台统一使用当前项目的 Ant Design 视觉体系。
10. 普通用户可以看到管理员发布的模型名称，但看不到渠道、供应商、密钥和内部路由。
11. 首期同时接入图片、文本、视频、音频 Relay。
12. 提供邀请机制，邀请奖励额度由管理员在后台配置。

### 首期范围

1. 用户端按图片、文本、视频、音频能力分组，并显示管理员发布的模型名称。
2. 首期不支持兑换码、发票、退款申请页和客服工单。
3. 首期支付只启用易支付，其他支付渠道留作后续扩展。

### 可运营配置

首期行为边界已经确认并写入第 7、9、10 节；邀请奖励的具体额度、每日上限、累计上限和风险规则由管理员后台配置，初始奖励值为 0。
